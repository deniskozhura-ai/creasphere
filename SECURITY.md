# Політика та архітектура безпеки CreaSphere (SECURITY.md)

Цей документ описує архітектуру захисту, правила доступу, валідацію та вимоги до розгортання в production для проєкту **CreaSphere**.

---

## 1. Автентифікація та сесії адміністратора

- **Пароль адміністратора**:
  - Налаштовується виключно через змінну оточення `ADMIN_PASSWORD`.
  - Заборонено зберігати або транслювати пароль на клієнт (frontend).
  - Порівняння паролів здійснюється за допомогою `crypto.timingSafeEqual`, що унеможливлює таймінг-атаки (timing attacks).
- **Сесії**:
  - Токени сесії генеруються криптографічно стійким генератором випадкових чисел `crypto.randomBytes(32).toString('hex')`.
  - Відсутні будь-які статичні або захардкоджені токени.
  - Токен зберігається в захищеному Cookie `creasphere_admin_auth` з прапорцями:
    - `HttpOnly: true` (недоступний для читання через JavaScript / XSS).
    - `Secure: true` у production (тільки по HTTPS).
    - `SameSite: 'lax'` (захист від CSRF міждоменних запитів).
    - `Max-Age: 604800` (7 днів).
  - Під час виходу (`DELETE /api/admin/auth`) сесія негайно анулюється на сервері та видаляється з браузера.

## 2. Авторизація та матриця доступу до API

Всі мутації та приватні дані захищені на рівні сервера за допомогою хелпера `requireAdmin(request)` у [`src/lib/auth.js`](src/lib/auth.js).

| `/api/custom-orders` | `GET` | **Тільки Адмін (401)** | Захист номерів телефонів клієнтів |
| `/api/custom-orders` | `POST` | Публічний | Заявка на дзвінок майстра |

## 3. Захист розрахунку цін замовлень (Anti-Price Manipulation)

- Клієнт передає на сервер лише ідентифікатори товарів та бажану кількість: `[{ id, quantity }]`.
- Сервер **ніколи** не довіряє клієнтським полям `total` або `price`.
- Для кожної позиції:
  1. Товар запитується безпосередньо з бази даних / каталогу.
  2. Перевіряється активність та статус товару.
  3. Перевіряється наявність на складі (`stock >= quantity`).
  4. Ціна береться **виключно** з бази даних: `serverPrice = product.price`.
  5. Сервер розраховує: `subtotal = serverPrice * quantity`, `orderTotal = sum(subtotal)`.
- Спроби передати від'ємну кількість, занижену ціну або нульову суму блокуються на рівні валідації.

## 4. Обмеження частоти запитів (Rate Limiting)

Для захисту від автоматизованих атак (DDoS, брутфорс, спам-боти) налаштовано ковзний Rate Limiter ([`src/lib/rate-limit.js`](src/lib/rate-limit.js)):
- **Вхід в адмінку (`admin-login`)**: не більше 5 спроб на 15 хвилин з однієї IP-адреси (захист від перебору паролів).
- **Створення замовлень (`create-order`)**: не більше 5 замовлень на 10 хвилин з однієї IP-адреси.
- **Публічні заявки (МК, оренда, кастомні вироби)**: не більше 5 запитів на 10 хвилин.
- При перевищенні ліміту повертається HTTP-статус `429 Too Many Requests` з заголовком `Retry-After`.

---

## 5. Валідація та захист від XSS / Mass Assignment

Усі вхідні дані проходять централізовану обробку через [`src/lib/validation.js`](src/lib/validation.js):
- Видалення HTML-тегів та небезпечних протоколів (`javascript:`, `data:`).
- Обмеження максимальної довжини рядків (захист від вичерпання пам'яті).
- Сувора типізація чисел (заборона `NaN`, `Infinity`, від'ємних значень).
- Strict Allowlist: невідомі поля відсікаються, запобігаючи Mass Assignment у базу даних.

---

## 6. HTTP Заголовки безпеки

У [`next.config.mjs`](next.config.mjs) налаштовано обов'язкові заголовки:
- `Strict-Transport-Security`: форсування HTTPS на 2 роки.
- `X-Frame-Options: SAMEORIGIN`: захист від Clickjacking.
- `X-Content-Type-Options: nosniff`: захист від MIME-sniffing.
- `Referrer-Policy: strict-origin-when-cross-origin`: захист конфіденційності реферерів.
- `Permissions-Policy`: заборона небезпечних API браузера (камера, мікрофон тощо).
- `Content-Security-Policy`: суворий контроль джерел скриптів, стилів, шрифтів та з'єднань.

## 7. Запуск автоматизованих тестів безпеки

Для перевірки захищеності всіх ендпоінтів та сценаріїв запустіть:
```bash
npm test
```
Тести перевіряють:
- Блокування неавторизованих спроб мутацій та читання приватних даних (401).
- Неможливість маніпуляції цінами у замовленнях.
- Роботу валідації та санітизації XSS.
- Роботу сесій та блокування брутфорсу (429).
